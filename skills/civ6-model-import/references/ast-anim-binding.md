# `.ast` 动画引用治理（增、删、降级）

> 与「路由三：从原版领袖 ast 复制后只改绑定与时长」互补——那条讲**初次生成**，本文讲**已有 ast 的引用增删**。

## 一、四处引用，少改一处就白改

一段动画在 `.ast` 里出现在四个容器中，必须同时处理：

| 容器 | 作用 | 漏改的后果 |
|---|---|---|
| `<m_Animations>` | 资产清单 | 动画仍被 cook 进包，体积不减 |
| `<m_timelines>` | 时间线定义（含时长、触发器） | 引擎可能仍能找到该时间线 |
| `<m_timelineBindings>` | 槽位 → 时间线 | 槽位仍指向它 |
| `<m_animationBindings>` | 槽位 → 动画资产 | 状态机仍会索引它 |

只删 `m_Animations` 是最常见的半吊子改法：包变小了，但槽位还在，行为不变。

## 二、两种"去掉"，语义完全不同

| 做法 | 实现 | 槽位是否存在 | 适用 |
|---|---|---|---|
| **降级为 IDLE** | 槽位保留，时间线/绑定改为 IDLE | 存在 | 想让该情境有动作，只是复用待机 |
| **不引用** | 四处容器都不出现该槽位 | 不存在 | 想让该情境不播动画（走引擎默认姿态） |

**先问清楚要哪一种**。把"不引用"做成"降级"，结果是该情境仍在播待机，用户会以为没改；把"降级"做成"不引用"，可能让状态机落到未定义姿态。

实现建议：在装配脚本里用两张显式表表达意图，不要用注释掉的代码：

```
IDLE_ANIMS = {角色: (动画名...)}   # 降级
DROP_ANIMS = {角色: (动画名...)}   # 不引用
```

两表对同一动画互斥，装配时断言交集为空。

## 三、文件保留，引用解除

需求常是"不引用即可，不要删除文件"。所以：

- 源动画的 `.fgx/.anm` **照常复制到工程 `Animations/`**（保留，便于随时恢复）；
- 只在 `.ast` 生成阶段过滤。

这样恢复成本 = 从 `DROP_ANIMS` 删一项 + 重装配，不需要重新烘焙。

## 四、验收

| 项 | 方法 | 期望 |
|---|---|---|
| 引用计数 | 正则统计 `.ast` 里 `<m_AnimationName>` 出现次数 | 目标动画 = 0 |
| 槽位计数 | 统计 `<m_SlotName>` 唯一值数量 | 按删除的槽位数等比下降 |
| 文件保留 | `ls Animations/<CODE>_<clip>.fgx` | 仍在 |
| 包体积 | 对比 cook 前后 BLP 字节数 | 明显下降（证明真的没打包） |
| 打包正确 | cook 四类告警为 0 | 全 0 |

体积变化是最有说服力的证据：如果 `.ast` 改了但 BLP 字节不变，说明改的不是生效的那份 `.ast`（或 cook 读的是旧的）。

## 五、红旗清单

- 改了 `.ast`、cook 成功，但包体积一点没变 → 改的不是 cook 实际读取的路径，或 cook 命中了缓存（见 `misattribution.md` 的基准纪律）；
- 槽位数没变 → 只删了 `m_Animations`；
- 实机仍在播 → `m_animationBindings` 没动；
- 恢复后动作变得很奇怪 → 恢复时只把动画名加回 `m_Animations`，没有补时间线与绑定。
